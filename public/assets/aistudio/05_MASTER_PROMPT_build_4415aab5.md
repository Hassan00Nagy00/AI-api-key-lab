## 2. CANONICAL DEFINITIONS (single source of truth — use these exact names everywhere)

**KEY STATUS** — the only allowed values of `ApiKeyRecord.status`:
- `untested` · `testing` (UI-transient; on startup becomes `untested`) · `working` (the LAST test completed a real generation AND passed Response Validation) · `rate-limited` (429/quota) · `unauthorized` (401 / provider invalid-key signal) · `forbidden` (403) · `no-credit` (402/insufficient balance) · `no-usable-model` (auth not rejected, but no generation-capable non-paid model could be selected, or model-not-found) · `provider-unavailable` (5xx/maintenance/gateway) · `network-error` (offline/DNS/TLS/timeout) · `blocked-or-network` (BROWSER ONLY: opaque fetch failure; may be CORS or network) · `config-error` (bad URL/template/adapter config, malformed response caused by config) · `unknown-error`.
- Orthogonal fields: `authVerified: "yes"|"no"|"unknown"`; `lastKnownGood?: {at, model, latencyMs, modelTier}` (set on every success, never cleared by failures).

**ERROR CATEGORY → KEY STATUS**
- 401 `auth` → unauthorized · 403 `forbidden` → forbidden · 402 `insufficient-credit` → no-credit
- 404 on models/chat endpoint `endpoint-not-found` → config-error · model not found/unsupported `model-not-found` → no-usable-model (then fallback)
- **PROVIDER SIGNAL PRIORITY:** the provider's own error signal (error code/status string/reason in the response body) overrides the HTTP-status table; the table is only the default when no known signal is present. Signals live in the registry as data (`errorSignals: [{ httpStatus, match, category }]`), e.g. an invalid-key reason delivered inside a 400 must map to `unauthorized`, and a 404 whose body says the MODEL is missing maps to `model-not-found` while a 404 on the path maps to `endpoint-not-found`. Every `errorSignals` entry is `needsVerification` until a golden fixture (recorded from a real response) proves it.
- 400/422 `bad-request` → config-error · 408/client timeout `timeout` → network-error · 409 `conflict` → unknown-error
- 429 `rate-limit`|`quota-exhausted` → rate-limited · 500 `server-error` → provider-unavailable · 502/503/504 `bad-gateway`|`service-unavailable` → provider-unavailable
- fetch failure (non-browser) `network` → network-error · opaque failure (browser) `cors-or-network` → blocked-or-network
- 200 + error object → classify by the error's own code · 200 + unparsable `malformed-response` → config-error · 200 + no usable output `empty-response` → unknown-error (then fallback)
- Never map CORS/network/timeout/rate-limit/server errors/model-not-found to `unauthorized`. A 429 with `authVerified="yes"` displays "Rate limited — the key appears valid".

**MODEL DIMENSIONS** (the only model statuses)
- `tier`: free | trial | paid | unknown · `tierEvidence`: provider-api | user | registry | naming-rule | none (strongest first) · `availability`: available | unavailable | deprecated | unknown · `observed`: {lastWorkingAt?, lastFailureCategory?} from real tests only.
- "Rate limited" is NOT a model status, only a transient test observation.
- Never set `tier="free"` without evidence other than `none`. Badge FREE only when tier is free (tooltip shows evidence); show "Tier unverified" when unknown.

**WHAT "WORKING" MEANS (two separate questions)**
1. Does the key work? → status `working` after a real generation succeeds on any non-paid model (free, trial or unknown tier).
2. Is a free model confirmed? → shown separately ("Free model confirmed") only when the successful model has tier free with evidence. The dashboard shows both counts. A valid key must not stay failed merely because the provider exposes no pricing data.
Never auto-select a `paid` model; use one only if the user selects it explicitly and confirms a cost warning.

**TEST REQUEST DEFAULTS**: message `Hi`; max output tokens 256; temperature unset; timeout 30 s (chat 120 s); no automatic retries except the fallback-model rule.

**RESPONSE VALIDATION** — success needs ALL: 2xx; no error object in body; parseable; non-empty visible text. Special case: reasoning/thinking output with no visible text and a length-limit finish → retry ONCE with double tokens; visible text appears → working; still reasoning-only → working with warning "reasoning-only output"; neither visible text nor reasoning → `empty-response` (not working).

**VERIFICATION LADDER** (cheapest first; only Tier 2 can produce `working`): Tier 0 list models (proves auth only where `modelsRequiresAuth=true`); Tier 1 optional token-count/dry endpoint when the provider offers one; Tier 2 real generation with "Hi". Record `authVerified` after each tier. A 2xx at Tier 0/1 alone never sets `working`.

**MODEL SELECTION** (single algorithm)
- Candidate filter: generation-capable per adapter metadata; availability not unavailable/deprecated; tier not paid; id not matching the provider's data-driven `excludeModelPatterns` (e.g. embeddings, TTS, image, live/realtime families) — patterns live in the registry, never in logic.
- Ranking: (1) user-selected model (if paid → require confirmation) (2) this key's `lastKnownGood` if still listed (3) live-reported free (evidence provider-api) (4) registry-recommended present in the live list (5) remaining candidates: if the tier is known free/trial, higher observed reliability then lower historical latency; if the tier is UNKNOWN (typical for Gemini and most providers), cheapest-first — never largest-first: (5a) registry `testModelPreference` entries (ordered, data, with `verifiedAt`) present in the live list, (5b) registry `cheapPatterns` matches (e.g. lite/flash/mini/small/nano/haiku — data in the registry, never hard-coded in logic), (5c) registry `avoidPatterns` (pro/opus/large/ultra…) last, (5d) smaller context window before larger (a heuristic, labelled as such). A model matching `avoidPatterns` is never auto-selected while any other candidate exists.
- Fallback on model-not-found / empty-response / rate-limit: next candidate; additional attempts configurable 1–3, default 2; show "Primary model failed. Trying fallback…"; never retry endlessly. No models API → use the registry list and mark `source="registry"`. Nothing qualifies → `no-usable-model` with "No verified generation-capable, non-paid model could be selected."

## 6. SECURITY
- **Display**: never show a full key after saving except via explicit Reveal (auto-hides after 15 s; not kept in state). Mask format `sk-or-v1-••••7F3A` (last 4 only). Provide Reveal/Hide, Copy (explicit click; clipboard auto-clear 30 s optional, documented as best effort), Edit, Delete, Test, Retest, Export configuration.
- **Never**: log keys, send them to analytics or an unrelated server, put them in URLs (use a header; query auth only when no header alternative exists), show them in errors, store them in chat messages. Redact by exact stored-secret match (and substrings ≥6 chars) plus patterns.
- **Storage tiers (be honest in the UI)**: browser vault = AES-256-GCM with a key derived from a USER PASSPHRASE (PBKDF2-HMAC-SHA256, ≥600,000 iterations, random salt) via WebCrypto, non-extractable key held in memory only, auto-lock after idle; without a passphrase show a persistent warning and do NOT claim encryption. Never store the same secret in two places. Prepare a `StorageService`/`SecretStore` abstraction so the desktop build can replace it with Keychain-backed storage without changing callers.
- **Host binding**: every key has `boundHost`. The secret is attached only if the request hostname equals `boundHost`, scheme is https (http only for explicitly approved local providers), and the URL has no embedded credentials. Changing the host (custom Base URL, edited/imported provider, registry update) requires a confirmation showing old → new host and resets the key to `untested`. Imported custom providers and remote registry changes are `untrusted` until approved. Never follow redirects with credentials (treat as `config-error`).
- **CSP**, safe external links (https only), input validation, minimal permissions, sanitized errors. Prepare (don't implement) Electron practices: contextIsolation, preload bridge, no Node in renderer, secure IPC.
- **CORS honesty**: a browser cannot distinguish CORS from network failure. Use `blocked-or-network` with: "The browser blocked or could not complete the request. This can be CORS or a network problem. It does NOT prove the key is invalid. Test this provider with the desktop app." Never classify it as unauthorized or working.
- **Import/export**: formats JSON, CSV, .env. Defaults mask keys. "Export Secrets" needs a strong warning and explicit confirmation. Import is schema-validated: reject unknown fields, files >10 MB and `__proto__`/`constructor`/`prototype` keys; imported records never carry secrets unless it is an encrypted backup; imported providers/hosts are untrusted until approved; duplicates detected by a salted key fingerprint (never the key).
- **Encrypted backup** ("Create Encrypted Backup", password-protected, also the migration path to the desktop build):
```
{ "format":"ai-api-key-lab-backup", "version":1, "createdAt":"ISO-8601", "encrypted":true,
  "kdf":{"name":"PBKDF2-HMAC-SHA256","iterations":600000,"salt":"<base64, 16+ random bytes>"},
  "cipher":{"name":"AES-256-GCM","iv":"<base64, 12 random bytes>","tagLength":128},
  "payload":"<base64 ciphertext+tag>" }
```
Bind format/version/createdAt/kdf/cipher.name as AES-GCM AAD; new random salt and IV every time; reject unknown versions/KDF/cipher names; wrong password → generic failure; schema-validate the decrypted payload before importing anything.
- **Destructive actions** — Delete key, Delete failed keys, Delete unused keys, Clear test history, Clear all data — always need a confirmation dialog that lists what will be removed (e.g. "Delete API Key? This will permanently remove: the API key, test history, associated configuration. [Cancel] [Delete]").
- **Custom provider security**: no SSRF-style abuse in the design (validate URL scheme/host, host binding), no unsafe redirects, controlled template/JSONPath parsing, schema validation, no dynamic code execution.

## 13A. ADDITIONAL V1 SPECIFICATIONS
- **Budget Guard (MUST).** Settings: `dailyGenerationCapPerKey` (default 20), `dailyGenerationCapGlobal` (default 100), per local calendar day, persisted in metadata. EVERY generation request (tests, fallbacks, health checks, later the gateway) goes through one budget service; at the cap: hard stop with a clear message (Playground: soft warning + confirmation). Tier-0 list calls have their own, separate counter and cap. When a key has unknown tier or the provider could bill, show once: "This account may have billing enabled; a model of unknown tier can be billed." Health checks never run for a key whose budget is exhausted.
- **Golden fixtures (MUST).** `scripts/record-fixtures.ts`, exposed as `npm run fixtures:record` and run only by the USER in their own Terminal: reads the key through a hidden (no-echo) prompt — never argv, never an environment variable, never a file; for a chosen provider it records real, sanitized responses for: model list, a valid "Hi", a wrong key, a wrong model id, and (optional) a rate-limit. Sanitizer removes the key, account/project/org IDs, request IDs, emails and token-like strings, and adds `recordedAt` and `providerId`. Output: `tests/fixtures/golden/<providerId>/<case>.json`. The user reviews `git diff` before committing. Contract tests feed each fixture through the adapter and assert the canonical STATUS and CATEGORY; fixtures older than 180 days are reported as stale. Golden fixtures are never described as live verification.
- **Canary-secret test (MUST, part of test:gate).** Plant a random `CANARY-…` secret as a key, run add/test/failed-test/retest/export (masked default)/diagnostics bundle/history/log flows against the fake server, then scan every output surface (console, storage dumps, history, exports, diagnostics, error messages) for the canary and any substring of ≥6 characters. Fail if found anywhere except the vault itself or an explicit, confirmed "Export Secrets" output.
- **Diagnostics bundle (MUST).** One button exports a redacted report (JSON + readable text): app version/build, OS/arch or browser, registry version, counts by status and category, the last N test records (provider id, model id, status, category, HTTP status, latency, time), non-sensitive settings, tool versions. Never: keys, fingerprints, prompts, responses, URLs with query strings, custom hosts (replace by a hash). It passes through the same redactor and is covered by the canary test.
- **Provider detection (SHOULD).** Registry `keyShape` per provider = `{ prefix, minLength, maxLength, charset }` — no arbitrary regex (so no ReDoS by construction). Pasting a key shows candidates as a SUGGESTION ("Looks like X — confirm"); ambiguous prefixes list all candidates. The key is never sent anywhere before the user confirms the provider (host binding applies after confirmation). Key shape is a hint, never validation. Prefix data is `needsVerification` until checked against official docs.
- **Expiry alerts (SHOULD).** Optional user-entered `expiresAt` (+ note) on a key. Dashboard card "Expiring soon", in-app banners at 7/3/1 days and when expired ("expired (user-declared)"); expired keys are skipped by scheduled checks. This is metadata only and never changes `status`. Be honest in the UI/docs: no notification can fire while the app is closed.
- **Model Watch (SHOULD).** A manual "Check for model changes" action (works in the browser build too) and, desktop-only (§ desktop prompt), an opt-in scheduled version. Tier 0 only — never a generation. One key per provider (prefer a working one), snapshot = set of model IDs + availability + time; diff reports new / removed / deprecated-marked. No "frozen model" detection (a list alone cannot prove it). Notifications are coalesced (at most one per day).
- **Quota snapshots (COULD).** Store rate-limit header values only from requests the app already made, with time; chart them; never predict a renewal date; "Provider limit unknown" when headers are absent.
- **Local assets.** Provider logos and icons are bundled locally (static files or inline SVG); no remote images (the CSP blocks them).
- **Chat history.** Browser tier: chat is saved unencrypted, so the "Save chat history" setting defaults to OFF with a clear explanation; secrets never appear in saved chats.
- **Backup duplicates.** Duplicate detection recomputes the salted fingerprint AFTER decryption with the local install's salt; fingerprints stored inside a backup are never trusted.
- **CI (deliverable).** `.github/workflows/ci.yml` on push/PR using `ubuntu-latest`: `npm ci --ignore-scripts` (plus reviewed scripts), lint, typecheck, test, test:gate, build, and a scan of the build output for secret patterns; `permissions: contents: read`; no secrets and no real keys; third-party actions pinned to full commit SHAs (if a SHA cannot be verified, say so in the report instead of guessing). A separate `release-check.yml` (manual `workflow_dispatch`, `macos-14`) is added only in the desktop phase.
